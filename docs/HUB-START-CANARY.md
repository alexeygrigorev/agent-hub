# Hub start canary (plan item 1.3)

Answers one question continuously: can Hub start a session that reaches a pane, today?
It uses only public CLIs (`hub sessions start|list|capture|stop`, `a list --json --running`).

## Probe (`scripts/hub-start-canary.sh`, logic in `scripts/hub_start_canary.py`)

1. `start`: `hub sessions start --no-wait --repo <project> --machine <local-host> --workspace <ws> --name hub-canary-<mode>-<run> --key canary-<run> --prompt <brief>`.
   Workspace is the root-owned `/etc/agent-hub/canary-workspace.json` value when that file exists, otherwise `$HUB_CANARY_WORKSPACE` or `~/work/hub-canary` (created mode 0700; keep it out of git; see below). Project defaults to `alexeygrigorev/agent-hub` (`HUB_CANARY_REPO`); machine defaults to `hetzner-aplexer` (`HUB_CANARY_MACHINE`). These timers run on that same local machine because native inventory uses its `a` binary. The returned host and workspace must match the request. The 180-second running deadline starts before the launch command; each subprocess is capped by the remaining stage time.
   The `hub` CLI has no tag/label option, so the canary identity is the `--name` prefix `hub-canary-`
   (use it to exclude canaries from picker stats and to auto-archive).
2. `running`: poll `hub sessions list --json` up to 180 s for state `running`.
3. `list_host_workspace`: the same row must carry a host (`host` or `machine_id`), a `workspace` and a `native_id`.
4. `capture`: `hub sessions capture <session_id> --json` must acknowledge actual output matching the expected marker. Headless local profiles on Linux use bounded stdout from their exact launch attempt; shell and interactive sessions retain pane capture. Explicit `--screen` capture always reads pane history. The host validates the task START record against the native parent, workspace, profile, prompt digest and launch time, and rejects symlink traversal. Full mode binds parser verification to the running session's `engine` and requires completed tool output in a single capture (Codex/ZAI completed `command_execution` with exit code 0; Go completed `tool_use`; Claude complete matching Bash `tool_use` and user `tool_result` with `is_error:false`, `interrupted:false`, empty `stderr`, and equal `stdout`/`content`, while a validated `run_in_background:true` / `backgroundTaskId` control result never proves marker output but does not invalidate a distinct completed Bash nonce pair; Antigravity complete matching `run_command` `step_update` `ACTIVE` and `DONE` frames with identical parameters and the anchored native exit-0 header). Assistant prose, `result` summaries, DONE-only/orphan frames, stitched captures, and prompt/command echoes never count. Full mode uses `CANARY-OK:<run-id>` and asks the model to concatenate separate tokens, so the complete marker never occurs in the prompt. Shell mode requires the exact `CANARY-OK` non-JSON output line.
5. `stop`: `hub sessions stop <id> --key canary-<run>-stop --wait`.
6. `gone`: the native id must leave `a list --json --running` within 60 s.

A `finally` always stops the session it created (`...-cleanup` key). If that fails the verdict says
`cleanup: FAILED_needs_reconciliation`.

Modes: `--mode full` (default; no engine, no model flag, a brief that first starts a separate bounded 60-second hold via the provider-native background tool facility, then runs a separate foreground shell tool call to print a nonce-bearing marker, and immediately enters a provider-native blocking monitor, `TaskOutput`, or status wait on that existing background hold task before any final prose or completion bookkeeping so the complete marker pair stays inside the 4096-byte tail capture window; allows mandatory Hub first-action/completion evidence files if required by the session wrapper; timer every 30 min and
after each deploy) and `--mode shell` (`--engine shell`, brief `printf CANARY-OK; sleep 30`; no model, timer
every 5 min). Shell contract (server, orchestrator-approved): engine=shell is headless only; the prompt is the literal OS command run via `/bin/sh -c` (Linux; Windows `cmd /d /s /c` unverified); no provider home; no reason or override needed (the canary sends no `--reason`). The 30 s sleep keeps the pane alive so capture and stop are observed. Capture passes only for the expected output line, allowing terminal gutter characters. No provider credential gate is invented.

Output: one JSON line on stdout (`ok, mode, run_id, timestamp, stage, reason, session_id, cleanup`), repeated on
stderr on failure. Exit 0 pass, 1 fail. Timeouts can be tuned with `HUB_CANARY_{RUNNING,CAPTURE,STOP,CMD}_TIMEOUT_S`,
`HUB_CANARY_POLL_S`; `HUB_BIN` / `A_BIN` replace the CLIs (tests).

## Workspace authority and pre-start admission

**Workspace.** `/etc/agent-hub/canary-workspace.json` is a fixed, root-owned, non-secret file read by the helper itself (not by the wrappers, which stay byte-for-byte unchanged). Shape: exactly `{"workspace": "<absolute normalized path>"}`. The reader refuses (stage `admission`, reason `workspace_config_*`) a symlink, non-regular file, owner other than root, `nlink != 1`, group/world-writable mode, size over 4096 B, unstable metadata, non-UTF-8/duplicate-key/extra-key JSON, a relative or non-normalized path, or untrusted ancestors (symlink, non-directory, non-root owner, group/world write). The file is read by UID 1000, so `root:root 0644` is the expected mode (not 0600). A valid file always wins over `HUB_CANARY_WORKSPACE`, including the value the forced wrapper injects after `env -i`; a present but invalid file never falls back. Only when the file is absent do the environment/default (`~/work/hub-canary`) apply, and then admission still runs. There is no environment or argument to select a different production config path. The new workspace leaf must be the invoking user's 0700 directory (existing private-directory check); parents may be user-owned 0775.

**Admission.** Before every call that can create a Hub session, the helper runs one fresh, finite admission: the main start, the idempotent start replay in cleanup (missing session id), and the missing-SID replay of a prior pending file. Replays keep the original recorded workspace, key, name and prompt, never retarget or clear the pending file, and when admission refuses the replay is skipped (the pending record stays and resolution continues by listing only). Stopping an already known session id is never gated. Admission time consumes the original active/cleanup deadlines; nothing is reset or extended and no ACK, cleanup or once proof is invented. A refusal before the first start leaves no session and no pending file (stage `admission`, closed reason). Checks, in order:

1. Disk floor: `GET /api/resource-settings` through the whole-archive-verified CLI (sealed candidate `hub.pyz`; periodic mode binds the owned `hub` zipapp or refuses `cli_artifact_unbindable`). The same fixed read-only GET bridge (also used for the current session inventory below) runs through that whole archive, never an extracted module or caller override: it proves before EVERY GET that the ACTUAL effective config (`config.load_config`, what the request really uses) equals the genuine human profile (`is_human_config`, `client_kind` human, no `_hub2_worker`/`worker_launch_id`) and refuses worker identity, `HUB_TOKEN`/`HUB_JOB_TOKEN`, `HUB_CONFIG_FILE`, worker/`HUB2` profile selectors and a `HUB_URL` that differs from the profile. It installs the caller's ORIGINAL finite physical budget as the maintained request deadline, which clips every GET and suppresses every 401 auth refresh; refresh, login and every config save are also trapped (hard exit), so there is never a refresh, config write, alternate profile, credential copy or API write. Typed holds: `resource_settings_unavailable|unauthorized|timeout|invalid`. A missing, unauthorized, unconfigured or out-of-range `disk_floor_gb` (1..1048576) refuses; there is no built-in floor.
2. Quota: fresh `quse --json`, raw output kept in RAM only. A successful process is not a pass: in full mode at least one route must be a supported native route (finite list below), status `ok`, fresh (< 20 min, not future), not stale/limit-reached/error/infinite, with every window (required and extra) well formed, `status` absent or `ok`, a finite 0..100 percentage and a parseable reset when one is given (a fresh zero-use reading without a future reset is valid), every required window group present and validated, and the lowest remaining above the provider reserve (Codex strictly above 15). Supported routes follow the Hub's actual native routes (claude, codex, go/opencode, zai via zcodex, antigravity via agy) with data semantics from quse `usage.py`/`gemini_quota.py` and the quota launcher's `provider_admission.py` (data only). Required groups (any alias satisfies one): Claude, ZAI (Hub account `zai-central`) and Gemini (quse key `gemini`, probe aliases `agy`/`antigravity`; Hub engine `antigravity`, account `gemini`) each need `5h` (alias `five_hour`) and `7d` (`weekly`, `seven_day`) with `monthly` optional; a missing or null Gemini `5h`/`7d` bucket is an unknown required window, not an unsupported provider. Codex and its distinct `codex-orin` account need `7d`/`weekly`, `5h` and `monthly` optional, with the strict greater-than-15 reserve; Go (quse `go`) needs `5h`/`rolling`, `7d`/`weekly` and a REAL `monthly`, nothing optional. Copilot-only, Grok (a quota label with no Hub native engine here; no Grok worker is launched or claimed) and unknown names can never make the canary eligible. An explicit window `error`/`stale`/`limit_reached`/`infinite` flag or non-`ok` `status` is refused before any optional-null handling. Only a source-proven optional slot of that provider that is entirely null (no percentage, no reset, `present` not `true`) is skipped; a null required or unlisted window, a `present` of `true` with null data, partial/reset-only data, `present: false` on a reading, a non-boolean `present`, a present-but-exhausted window and a missing required group all refuse. This is data validation only: the launcher's executor lifecycle and its independent Codex execution prohibition are not imported, the protected Codex wrapper and 15% reserve stay authoritative, and the authenticated Hub picker remains authoritative for the account (none is pre-selected or proven). Shell mode requires a fresh valid acquisition only.
3. Native residency from the CURRENT inventory (`a list --json`, no `--all` history) plus managed in-flight Hub rows (the complete current paginated `GET /api/sessions?live=1&limit=100` (always `live=1`, never the history form; cursor appended encoded) through the same read-only bridge, not the ordinary `hub sessions list`, whose 401 path could refresh and save credentials; at most 100 rows per page, bounded pages and 5000 rows, unique ids, unique cursors, `complete` consistent with the cursor, one original deadline; any incomplete/repeated/duplicate/invalid page holds `managed_inflight_invalid`, 401/403 or any profile mismatch `managed_inflight_unauthorized`, an exhausted budget `managed_inflight_timeout`, else `managed_inflight_unavailable`; this machine only, terminal states ignored, unknown states hold). A row is released as dead only when `worker_alive` is `false` and either `containment_empty` is `true`, or (older terminal rows where aplexer left it NULL/absent) the row is `exited`/`failed` and any current cgroup it names is gone or has no members; missing historical pid/cgroup metadata alone is not a live obligation, and dead rows join no identity map or reserve. `phase`/`state` alone, an unknown or absent `worker_alive`, `containment_empty: false`, or a named cgroup that still has members never release a row. Every live row first resolves its CHOSEN PID and cgroup, before the duplicate/shared maps: the workload, unless its PID is `None` (not a starting row) or opening `/proc/<pid>/stat` actually returns ENOENT, in which case the same census row's native coordinator (`worker_pid`/`worker_cgroup`) is chosen, and only when that row's `worker_alive` is exactly `true`. Nothing else falls back: an existing PID (identity, cgroup, membership or start mismatch), EACCES or other errors, an invalid PID type, a missing measurement file of an existing workload, or an unproven worker all hold as before. A coordinator is proven only by its own fresh kernel state, never by the workload's recorded scope, identity or caps: matching boot id, cgroup and mount namespaces, the PID's single `0::` cgroup equal to the chosen path, a no-follow cgroup directory fd (dev/inode equal to the path), membership, stable start ticks across two samples, SDK `created_at_ms` within [-30 s, +2 s] of the kernel start (`btime` + start ticks; the window the current-launch qualification approved), and positive own `RssAnon` plus group `anon <= current` in both samples (the cgroup may hold other processes). A stable coordinator of age >= 180 s in `running`/`running` reserves 0 extra even with `memory.max = max` (already in `MemAvailable`; no growth guarantee). A younger or uncertain one reserves its actual finite kernel `memory.max` in full per row (never divided, never the workload's 1500 MiB limit) and holds (`resident_bound_unknown`) when that is `max`. Chosen PIDs must be distinct across rows (`resident_identity_ambiguous`). Just before the final `MemAvailable` sample, if any coordinator was used, the helper re-reads the census once (same original deadline; no renewal, no extra poll), validates its ids exactly like the initial inventory (UUID, case-insensitively unique; a duplicate, invalid or missing final id is an ambiguous snapshot and holds `resident_fallback_changed`), and re-samples each chosen coordinator: any change of the sampled census identity fields (including a workload that appeared or was replaced), the workload premise, or the chosen PID/start/cgroup identity holds (`resident_fallback_changed`). Typed reasons: `resident_identity_unknown|unstable`, `resident_measurement_unknown`, `resident_anonymous_unknown`, `resident_bound_unknown`, `resident_fallback_changed`. **Current workload proof (unrecorded identity).** A live row whose workload PID exists, whose `worker_alive` is exactly `true` and whose `containment_cgroup_identity` is UNRECORDED, i.e. the key is MISSING or the WHOLE value is `null` (the public SDK field is `Option<CgroupIdentity>` with serde default and skip-None; both forms are the same absence, a documented revision of the earlier missing-key-only rule; this asserts nothing about what any installed SDK emits), and which is not an empty or partial dict, a wrong type or a dict with a `null` inside, keeps that SAME workload PID as its chosen target (never the coordinator) and is proven only from fresh kernel state, with no SDK rewrite and no old-record credit: the kernel cgroup is derived from the single `0::` line of `/proc/<pid>/cgroup` (strict relative path; an optional recorded `workload_cgroup`, itself `Option<String>`, is unrecorded when missing or `null` and then the derived kernel group of the same PID is used, while a present value must be valid and equal it) and resolved BEFORE the duplicate/shared maps; then the same two-sample proof as the coordinator applies (boot id, cgroup and mount namespaces, no-follow cgroup fd dev/inode against the fresh path, membership before and after, stable start ticks, SDK `created_at_ms` within [-2 s, +30 s] of the kernel start, positive own `RssAnon` and group `anon <= current`). In a shared cgroup only the selected PID's own anonymous memory counts; another process or the whole group is never credited. Mature (>= 180 s, `running`/`running`) reserves 0 extra even with `memory.max = max`; a younger or uncertain one reserves its ACTUAL finite stable kernel `memory.max` whole per row, never the SDK limits, the 1500 MiB default or a share of the group, and holds (`resident_bound_unknown`) otherwise. A PROVIDED (non-null) identity that is not valid for this boot/namespaces (empty/partial dict, `null` inside the object, wrong boot or namespace inode, invalid type), a contradictory or malformed recorded group, an unproven worker, PID reuse, a birth outside the window, permission/parse/size errors or any unknown measurement is a HOLD: a correct current kernel proof never erases an explicit contradiction. The final census re-read (and, for this proof, one managed in-flight re-read) must show the same rows, presence/value of the recorded identity (a missing to `null` change, either way, is a changed snapshot and holds), selection and uncovered in-flight set, and a final kernel re-sample must show the same identity (and cap for a young row), under the same original deadline, else `resident_fallback_changed`. Every other live row keeps the identity-bound proof, now taken with the same strong kernel sampler as above but for the CHOSEN workload PID only: a worker already counted in `MemAvailable` reserves 0 extra only with matching boot id and namespaces, the workload PID alone in its recorded cgroup (single `0::` line), a no-follow scope fd and a held cgroup MOUNT ROOT fd whose dev/inode/`mnt_id` and fresh paths stay identical before and after the memory reads, stable start ticks and chosen-PID membership over two samples under the one original deadline, process age >= 180 s on `CLOCK_BOOTTIME`, and positive anonymous memory (own `RssAnon` for a shared cgroup; also cgroup `anon <= current` otherwise). The other members of the cgroup are NOT compared: a tool child joining or leaving between samples no longer fails the proof (previously the whole `cgroup.procs` set had to be equal, `resident_identity_unstable`), while the chosen PID leaving, being reused, moving or changing namespace/scope/root still refuses. Every sample (coordinator, current workload and provided) ends by re-reading the chosen PID's and this process's cgroup/mount namespaces (dev and inode): the initial chosen, initial self, final chosen and final self tuples must all be one object (and the provided coordinates were already proven against it), so a namespace switch during the memory reads holds (`resident_identity_unstable`; unreadable `resident_measurement_unknown`). Every PRESENT recorded coordinate is validated strictly before any credit and again at the final check: `boot_id` equal to the current boot, `cgroup_namespace_device/inode` and `mount_namespace_device/inode` equal to the real namespace stat, and `cgroup_root_device/inode` and `cgroup_mount_id` equal to the held cgroup MOUNT ROOT fd and its `fdinfo` `mnt_id` (never the workload scope's inode); each must be a positive integer (bool, float, string, null, zero, negative or an unknown key holds `resident_identity_unknown`). Coordinates that are missing stay boot-only compatible and are proven freshly from the kernel, never invented or rewritten. Measured provided workloads are part of the final re-check (census re-read, one managed in-flight re-read, a final chosen-PID sample under the same deadline, `resident_fallback_changed` on any difference). For a young credited row the final credit is the minimum of the first, second and final positive accounting anonymous memory (own `RssAnon` when shared, validated group `anon` otherwise); the unchanged cap-minus-credit reserve is recomputed and only a non-negative increase is added, once, before the final `MemAvailable` sample, so a falling anonymous usage raises the reserve and a rising one never lowers it; a whole-cap reserve is never reduced, a mature row keeps 0 extra but needs a positive final chosen anonymous sample. `memory.max = max` does not disqualify this; it only means no future-growth guarantee. Young or starting workers reserve their recorded finite memory limit (minus proven anonymous use); an unknown limit, identity, measurement or age holds. Managed in-flight rows without a native row reserve the 1500 MiB ceiling, never the possibly smaller selected cap.
4. New-worker caps: the helper reads the Host's selected config, `~/.config/agent-hub/v2.json` (the `hub2` CLI default; the Host unit passes no `--config`), in RAM only. It never prints or persists the file, token or environment and keeps only `machine_id` and `launcher.memory_mb`/`launcher.pids`. The file must be a regular NOFOLLOW file, owner-private (0600, `nlink` 1, at most 256 KiB, stable across the read) under a private user-owned directory, with unique-key JSON and `machine_id` equal to this canary's machine; the caps follow `native_launch.py` (`--memory <memory_mb>M`, `--pids`, defaults 1500 / 256 only when the keys are absent). Null, bool, string, float, zero or negative values, caps above 1500 MiB / 256 PIDs, or an unreadable, unsafe or mismatched file hold admission; there is no caller or environment bypass (tests inject a seam). The actual memory value is used in the RAM arithmetic. To tie the file to what the Host loaded, exactly one Host daemon process of this user must exist in the `agent-hub2-host.service` cgroup, either today's `hub2 serve` or the release interpreter of `hub host serve` (strict leading argv `<home>/.local/share/agent-hub2/releases/<id>/bin/python*`, `-I`, `-m`, `agent_hub_host.cli`, `serve`; a canonical absolute lexical path, the venv interpreter may itself be a symlink and is never resolved; no substring or `-c`/late `-m` match), run from this home's `agent-hub2` tree with no `--config` anywhere in argv, with a daemon `HOME` equal to the selected home and a stable start time, and both mtime and ctime of the config must be strictly earlier than that process start; otherwise admission holds (`launcher_config_*`).
5. Disk, per device of the resolved workspace and its `.local/tmp` (one charge per device): validated floor + 512 MiB start spike + 512 MiB for this new worker's own known growth + 512 MiB per live current worker or uncovered in-flight task whose workspace/cwd/`.local/tmp` is on that device, capped at 8192 MiB; a RAM-mature worker is charged too (RAM proof says nothing about disk), terminal history is not, and a live worker or in-flight task whose location cannot be resolved holds (`disk_growth_unknown`). The 512/8192 MiB figures mirror the maintained quota-launcher disk gate (`launcher_recovery.py`); that gate's linkage to NativeLauncher starts is not proven here, so they are a bounded conservative estimate, not a measured growth bound or a guarantee.
6. RAM: a final fresh `MemAvailable` minus uncovered reserves minus the actual selected new-worker memory must be at least 10 GiB. PIDs are only checked against the 256 ceiling.

Limits, stated plainly: the coordinator, current-workload and provided-identity proofs are current samples of generic kernel/census metadata only (no participant, history, SDK or capture probe) and the census may churn between the two reads, which holds and is retried by the next run rather than looped; this is per-attempt sampling, not kernel-atomic admission (independent Host/native writers can race between sample and dispatch); a mature resident's zero RAM reserve is not a future-growth guarantee and disk growth beyond the estimate is unknown; the helper cannot see systemd drop-ins or the daemon's full environment, so the Host process/config binding is evidence of the selected caps, not an attestation of the loaded values; the launcher's `aplexer` selection is not compared with the canary's own `a`. Installing the helper, the root config and the matching bundle is a Root coinstall under the existing deploy lock; this document is not evidence that any of it is installed.

### Read-only physical preview (`--physical-admission-check`)

`hub_start_canary.py --physical-admission-check` (no other option) runs BEFORE any `Canary` construction, lock, key, pending/once/state file or alert action. It builds only the read-only `PhysicalAdmission` base class that `Canary.admit` also uses and runs the same `physical_inputs` (launcher caps, validated disk floor via the human-profile bridge) and `physical_admit` (current census, in-flight rows, target selection, residency, disk growth/floor, final revalidation and the final `MemAvailable` arithmetic). It reads the fixed root workspace config (or the default), never an argument or environment value (`HUB_BIN`, `A_BIN`, `HUB_CANARY_*` are ignored); it acquires no provider quota, starts, captures, stops or sends nothing, refreshes no auth (the bridge above is its only network path: resource settings and session inventory) and writes no state or config. Output is one bounded JSON line: source SHA, `ok`/`status`/`reason`, `quota_checked: false`, `full_admission: false` and closed counts/headrooms (census, live, mature, young, kernel-current, coordinator-fallback, uncovered in-flight, reserve, new-worker bytes, RAM and disk headroom); no ids, tags, PIDs, cgroups, paths or raw errors. Exit 0 pass, 1 hold. It is a fresh sample only and never authorizes a start; a full admission (fresh quota and every gate) still runs at the real start.

## Codex/ZAI config bound (startup recovery)

Managed Codex/ZAI `config.toml` reads and writes use a dedicated 1 MiB bound (`host/agent_hub_host/provisioning.py`); generic `private_fs`, auth, secret, JSON and hook limits are unchanged. A present file that is oversize or invalid UTF-8 fails closed: no empty defaults, no truncation or settings loss, and a generated file over 1 MiB is not published. The retained POSIX behavior tightens an existing 0644 engine file to 0600 before the size/UTF-8 refusal, so a refused file may still have its mode changed (refusal is not mutation-free); an `EngineTomlConfigError` also aborts the install before other providers are provisioned when no provider is selected. The actual generated size that failed on the live Host is unknown and live Codex acceptance still needs a legitimate rollout.

## Alerting

State: `${HUB_CANARY_STATE_DIR:-${XDG_STATE_HOME:-~/.local/state}/agent-hub-canary}` (dir 0700, files 0600), one state file per mode.
Two consecutive failures send ONE mail to `dev@dtcdev.click` (fixed in code; never orin@, no CC, not env-configurable)
through `msmtp -a alerts -f alerts@dtcdev.click`, the same path as `resource-gate-monitor.sh`. Subject and body carry
stage, typed reason, timestamp and run id. No repeat while the incident is open (also when failures continue or one
success interrupts them). After two consecutive successes one `[RECOVERED]` mail is sent and the incident closes.
A failed send is retried on the next run. Tests inject `HUB_CANARY_MAILER` (a command receiving the message on stdin)
and never call real msmtp.

## Deploy gate

`scripts/hub-start-canary.sh --deploy-gate` runs the full-mode canary once (needs an LLM start); `--deploy-gate --mode shell` runs the cheap shell canary instead (default stays full). It sends no mail and touches no alert
state. Exit 1 prints the JSON verdict on stdout and stderr, e.g.
`{"ok": false, "stage": "running", "reason": "state_failed:engine_not_allowed", "mode": "full", "deploy_gate": true, ...}`.
`deploy.yml` is not edited here; the head wires the last deploy step to run this and trigger the existing rollback on non-zero exit.
Allow ~7 min worst case, including bounded failure cleanup. Note the VM that runs deploy needs the `hub`/`a` logins; the canary must run on a host with
`a` (Hetzner), e.g. over SSH.

## Install

`sudo bash scripts/install-hub-start-canary.sh [--user NAME]` (idempotent; installs scripts to
`/usr/local/sbin/hub-start-canary/`, four units to `/etc/systemd/system/`, enables both timers).
`bash scripts/install-hub-start-canary.sh --verify` renders units into a temp dir and runs `systemd-analyze verify`
without installing anything.
Units: `deploy/hub-start-canary.{service,timer}` (shell, 5 min), `deploy/hub-start-canary-full.{service,timer}` (30 min).

## OPEN QUESTIONS

- Windows hosts: shell prompt via `cmd /d /s /c` is unverified.
- A deployed server must include the projection and CLI fixes from PR391; older releases omit workspace or lack `--no-wait`. The canary
  fails at `list_host_workspace` until the server reports them. Intended.
- Capture uses the row's `native_id`; whether headless (non-interactive) sessions keep a pane for `a capture` is unverified.

Ambiguous start receipts are retried once with the identical key and payload during bounded cleanup. A recovered session is stopped; repeated response loss is reported as `FAILED_needs_reconciliation`, never `not_needed`. Current CLI pagination is exhausted with `sessions list --all --json`; the aggregated `sessions` array takes precedence over any retained first-page `items`. Incomplete cursor results fail explicitly. Stage deadlines also cap capture, stop and native disappearance checks; late success does not pass.

Headless stdout capture uses descriptor-relative no-symlink file reads on Linux. Platforms without that primitive retain their existing native launch and pane capture behavior; headless file capture there remains unverified. A capture acknowledgement is limited to a 4096-byte stdout tail and an 8000-byte JSON payload, below the server command-result ceiling. No stderr or raw START/RESULT record is returned.
