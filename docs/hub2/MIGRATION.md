# Hub 2.0 migration plan

Status: proposed sequence, revised 4 November 2026. This document does not authorize migration. The current Hub is reported disabled behind a 503 stub; that report is not an inspected database snapshot. No production resources, services, routes, credentials or data change in this architecture task.

All imports record source ID/version and migration generation. Source exports are immutable private recovery artifacts with hashes, outside public Git, encrypted where necessary. Do not delete source rows/services or existing scratch. A 503 Worker does not establish that its Durable Object databases are empty: obtain an actual read-only retained database export through an approved path. Source code and a native census cannot reconstruct lost asks, grants, message keys or schedule state. If the export is unavailable, record missing classes as unknown and stop parity acceptance; activate a fresh empty service only under a separately explicit data-loss decision.

## Staged cutover

1. **Implement and measure locally.** Complete the retained contract matrix and Linux/Windows vertical slice, schemas, auth, export/import and instrumentation. Validate with synthetic credentials, representative retained history, forced eviction/reconnect, crash points and Wrangler dry run. <=6,000 authored production LOC and <20,000 normal-day combined operations are gates to prove, not assumed results. Measure populated index creation and migration separately.
2. **Inventory consumers and capture source.** With future authorization, inspect then-current skills, clients/hosts, schedules, webhook sources, grants, queues, native census and available API telemetry. Reconcile the known local skill-version discrepancy for repository selection. Take a consistent read-only database export plus host journal/census snapshot, record versions/hashes and verify class counts/ID sets. Missing data is unknown, not zero.
3. **Rehearse parity in isolation.** Import a sanitized representative export idempotently into disposable local shards. Compare every data class above, including all historical asks and registry metadata, not only totals. Repeat import, interrupt each step, rebuild directories and replay outboxes. Verify prefix/search/page behavior and current authorization. Contract/load tooling and its handwritten glue count under the architecture's stated line-count policy.
4. **Prepare compatible clients and hosts.** Build a compatible CLI release without changing the production endpoint. Use isolated test host configuration and synthetic identities for transport/provisioning tests; do not enroll against or mutate production before approval. Preserve existing native journals and services. Verify local launcher/resource refusals, native Windows behavior and one-time approval flows.
5. **Approve activation and fence old writers.** Before a production window, agree custody, write freeze, data snapshot, endpoint change, rollback mode and schedule state. If an old service is writable, fence all writes/effects, including start/send, receipts, claim updates and credential refresh, before the final export. Preserve running native sessions; no external service retirement without acknowledged handoff. Drain or preserve in-flight operations explicitly; do not create dual dispatch owners.
6. **Import disabled and reconcile.** Import the final snapshot with queue/schedule/alert effects disabled. Re-read native census and host journals. Reconcile reservations, ambiguous launches, wake delivery, provider generations, claims, report forwarding and message route epochs. Reapprove identities and map grants; old tokens stay invalid. Verify exact IDs/digests/sequences and owner routes. Arming a due job is an explicit step after parity, never an importer side effect.
7. **Switch only after explicit production approval.** Enable the approved Worker endpoint and test-host path. Verify login/CSRF/revocation, registry list/show/edit, intake history/search, one AC-gated native start, send/ack/report/stop, named-agent delegated inbox and a cross-host reply. Keep general schedules disabled until these pass. Check both safety and useful first activity rather than a queued status.
8. **Ramp fleet and explicit jobs.** Enable root/writer, configured orchestrator/on-call prompts, reset discovery/alerts, recovery deadlines and approved webhook sources incrementally. Observe warm/cold/reconnect row totals, queue progress, host freshness and Free-plan limits through a defined accepted observation window. Pause predecessor routines only after acknowledged replacement coverage, preserving their recovery path. Budget pressure never disables correctness reconciliation or silently drops work.

A disabled 503 endpoint may make this first activation rather than a live dual-write cutover. It does not relax export/parity requirements or authorize resource creation. Publication, enrollment, provider credential rotation and schedule firing in this sequence are future actions gated by production approval.

## Rollback and first-activation recovery

Before switching traffic, designate and rehearse one of two actual recovery targets:

- **Compatible prior v2 exists:** pin its code/schema version and prove it serves the imported database, including new indexes/rows and incomplete journals.
- **First v2 activation:** there is no assumed previously validated v2 to route back to. The prepared recovery mode disables new starts/sends/schedule effects while keeping authenticated read/export and reconciliation available. Running native sessions retain custody. The legacy 503 stub is not an operational fallback unless Alexey separately approves restoring a validated legacy service.

If auth, parity, dispatch or normal-day budget fails:

1. Disable new dispatch and optional schedule effects. Keep authorization, native receipt ingestion, report forwarding, reservation reconciliation and required attention events functioning; do not kill native sessions merely to reduce row use.
2. Preserve v2 databases, owner directories, queues, saga/outbox journals, host journals and exports. No namespace reset, destructive schema reversal or deletion.
3. Reconcile every uncertain offer/process against its native UUID and persisted operation journal. Expiry alone frees an unclaimed offer, never capacity held by an isolated running process. Require confirmed native exit or an accepted isolated handoff before replacement; retain old capacity/claims until then.
4. Route to the rehearsed compatible version when available; otherwise enter the first-activation recovery mode. Export all post-activation asks, grants, messages, keys, route epochs, reports and schedule progress before any alternative replay. Never re-run launch intents from a raw pre-cutover snapshot.
5. Report failed gates, missing evidence, current custody and the corrected replay plan. Keep source and import mappings until the parity/observation owner accepts them; approval of another attempt is not implied by this plan.

No deployment, production reads, route change, queue drain, credential rotation, cleanup or rollback was performed for this documentation revision.
