### 2.2 Adjudication of `M15-IG4`: Explicit `Z`/`±HH:MM` Offset vs Separate `limit_zone`

The prior review's `M15-IG4` summary table phrased the reset rule as *"Timezone-naive reset strings or missing `limit_zone` stay `limit_blocked_unknown_reset`"*, whereas the prior review's `M15-F4` Required Fix ([SESSION-LIFECYCLE.md](file:///home/alexey/git/agent-hub-wt-platform-lifecycle-r2-review/docs/reviews/SESSION-LIFECYCLE.md#L108)) specified *"require either an explicit offset in `limit_reset_at` or a valid IANA/UTC `limit_zone` (with `reset > now`) before classifying a limit reset as known"*.
- **Technical Adjudication**:
  1. An ISO-8601 timestamp carrying an explicit `Z` or `±HH:MM` UTC offset (enforced by `/T.*(?:Z|[+-]\d{2}:\d{2})$/i` in both `ISO` and `_parse_ms`) already encodes an unambiguous UTC instant (`epoch_ms`) that evaluates identically under `TZ=UTC` and `TZ=Europe/Helsinki`. Requiring a separate `limit_zone` string when `limit_reset_at` already carries `Z` or `±HH:MM` adds no disambiguation.
  2. Conversely, when `limit_reset_at` is timezone-naive (e.g. `"2026-10-21 13:16"` or `"2026-10-21T13:16:00"`), the R2 implementation rejects it (`null` / `None`) **even if a named `limit_zone` (e.g. `"Europe/Helsinki"`) is supplied**, classifying the session as `limit_blocked_unknown_reset` (`flags: ['limit_unknown_reset']`). That is strictly **more fail-closed** than `M15-IG4`, because resolving a naive wall-clock timestamp against an IANA zone requires a DST-aware timezone database conversion not present in this pure seam.
  3. **Gate Clarification (`M15-IG4`)**: In the M15a/b pure seam, `resetKnown` holds if and only if `limit_reset_at` carries an explicit `Z` or `±HH:MM` offset, parses to a finite epoch instant `reset > now`, and never guesses local or UTC zones; timezone-naive, missing, unparseable, or expired/present (`reset <= now`) reset strings unconditionally remain `limit_blocked_unknown_reset`. If a future `M15c`/`M15d` host adapter ingests provider reset strings that pair a naive wall-clock time with an IANA `limit_zone`, the host/server adapter must either convert them via `Intl.DateTimeFormat` / Python `zoneinfo` into an explicit-offset ISO timestamp with verified DST handling or leave them `limit_blocked_unknown_reset`.
